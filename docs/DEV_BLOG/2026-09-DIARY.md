# Development Diary - September 2026

---

## 2026-09-28: iOS build needs DXVK's nested header submodules

A fresh iOS build stopped in the DXVK meson configure step with
`ERROR: Problem encountered: Missing Vulkan-Headers`. The README's
iOS quick start ran `git submodule update --init references/fbraz3-dxvk`
without `--recursive`, so the fork's own `include/vulkan` and
`include/spirv` submodules were never checked out. The macOS build can
fall back to the Vulkan SDK headers, but the iOS cross build uses the
iPhoneOS sysroot and has no such fallback.

- `README.md`: the iOS quick start now uses `--recursive`.
- `cmake/dx8.cmake`: the iOS configure fails early with the exact fix
  command when those headers are missing, instead of failing deep in
  the ninja build.

## 2026-09-28: DXVK fails to compile against the iPhoneOS 27 SDK libc++

Building DXVK with Xcode's iPhoneOS 27.0 SDK stops in
`src/dxvk/dxvk_pipemanager.cpp` with libc++ errors from `<tuple>`
("a parameter pack may not be accessed at an out of bounds index",
"no member named '__base_' in 'std::tuple<>'").
`createNullFsPipelineLibrary()` builds its map key with
`std::piecewise_construct` and an empty `std::tuple()`, which that
libc++ no longer accepts. The key is already a default-constructed
local, so `Patches/dxvk-ios.patch` now passes `std::tuple(key)` instead;
the resulting key is identical.

A checkout that already applied the previous patch must reset the fork
first (`git -C references/fbraz3-dxvk checkout -- src`) so the configure
step can apply the updated patch.

## 2026-09-28: iOS packaging fails with duplicate signing certificates

`package-ios-zh.sh` re-signed the app with the name "Apple Development".
With two identical Apple Development certificates in the login keychain
(easy to end up with on a free Personal Team), codesign stops with
"ambiguous" and the app is never installed. When `GX_SIGN_IDENTITY` is
not set, the script now re-signs with the SHA-1 of the certificate Xcode
used for the provisioning shell app, which is also the one the
provisioning profile expects.

## 2026-09-28: iOS install picks a word from the device name

`package-ios-zh.sh --install` took the third-from-last column of
`devicectl list devices` as the device id. Model names with spaces
("iPad Pro (11-inch) ...") shift the columns, so it passed "Pro)" to
`devicectl device install`. The script now matches the identifier
pattern itself and accepts `GX_DEVICE_ID` as an override.

## 2026-09-28: iPad taps land in the wrong place (pillarbox + portrait launch)

On an iPad mini (A17 Pro) the main menu took one tap and then ignored
input. The log showed `Pillarbox: game=800x600, backbuffer=2266x1488`
and no `iOS internal resolution set to` line. Two bugs combined:

- `SDL3Main.cpp` injects `-xres/-yres` from the window pixel size only
  when the window is landscape. An iPad held in portrait at launch reports
  a portrait window before iOS rotates it, so the injection was skipped
  and the engine stayed at 800x600 behind a pillarbox. The app is
  landscape-only, so the long side is now always used as the width.
- `DX8Wrapper::Pillarbox_Setup()` took the backbuffer size from the
  present parameters (pixels) but left the pixel density at 1.0, so
  `Pillarbox_Get_Rect()` returned a pixel rect while touch/mouse input
  arrives in window points. On a 2x display every tap mapped to about
  half its real position. The density now comes from the window even when
  the size comes from the present parameters. Desktop windows are not
  created with high pixel density, so their density stays 1.0.

## 2026-09-28: iPad display collapses into a corner after a device reset

With the resolution fix in place, the main menu worked, but entering the
LAN lobby reset the D3D device and the log showed
`Pillarbox: game=2266x1488, backbuffer=1488x2266`. SDL keeps reporting the
window in portrait on an iPad launched in portrait, even though the
landscape-only app is displayed in landscape, and the reset sizes the
backbuffer from the window. The landscape game was then pillarboxed into a
portrait backbuffer and shown in the bottom-left quarter, with input mapped
to the wrong rect. The SDL3 display size providers in `W3DDisplay.cpp` now
report the long side as width on iOS.

## 2026-09-28: Root cause of the portrait window on iOS: missing SDL_HINT_ORIENTATIONS

An iPhone (A19, launched upright) showed the game squished into the left
half. The log had `iOS internal resolution set to 2622x1206 (window
1206x2622)` and `Created 3 swapchain images with size (1206, 2622)`.

SDL's `UIKit_GetSupportedOrientations()` returns *all* orientations for a
`SDL_WINDOW_RESIZABLE` window when `SDL_HINT_ORIENTATIONS` is unset, so the
view controller allowed portrait and `SetupWindowData()` sized the window
from the portrait screen. This is the common cause of the earlier iPad
issues too (stale portrait window size, portrait backbuffer after a device
reset). `SDL3Main.cpp` now sets the hint to `LandscapeLeft LandscapeRight`
before SDL video init, which makes SDL create the window landscape and keeps
the view controller landscape-only. The earlier landscape normalizations
stay as a defensive fallback.

## 2026-09-28: Log OpenAL device startup in release builds

An iPhone had no sound and the on-device log said nothing about audio:
`OpenALAudioManager::openDevice()` only reported failures through
`DEBUG_LOG`, which release builds compile out, and fell back to "sound off"
silently. It now also writes to stderr when audio is disabled by settings,
when `alcOpenDevice` / `alcCreateContext` / `alcMakeContextCurrent` fail
(with the ALC error code), and which device it opened on success, so the
iOS log can tell a failed device apart from a muted one.

## 2026-09-29: On-screen keyboard can be closed and opened on demand (iOS)

Naming a save game opened the iOS keyboard, which then covered the screen
with no way to close it: `updateTextInputState()` restarted text input every
frame while the entry field had focus, and iPhone keyboards have no hide key.

- `SDL_HINT_RETURN_KEY_HIDES_IME` is set on iOS, so Return closes the
  keyboard (the Return key press still reaches the game).
- When SDL stops text input behind the engine's back (Return, iPad hide
  key), the engine remembers the entry field and keeps the keyboard closed
  until focus moves elsewhere.
- The focused entry field's rect is passed to `SDL_SetTextInputArea()` so SDL
  slides the view up and keeps the field visible above the keyboard.
- New floating keyboard button, drawn translucent on top of the UI
  (`SDL3TouchOverlay_Draw()`, called from `W3DDisplay::draw()`): tap to show
  or hide the keyboard at any time (with no entry field focused, typed keys
  reach the game as key presses); long-press then drag to move it. The
  position is saved to `Documents/touch-keyboard-button.txt`. Touches that
  start on the button never reach the gesture translator.

The button's touch state machine and drawing were exercised off-device
against the SDL 3.4.2 headers (tap toggles, taps elsewhere pass through,
long-press drag moves and persists the position).

## 2026-09-29: Keyboard button stays reachable, tap-outside closes, no predictive bar

Follow-ups to the on-screen keyboard work, from device testing:

- The floating keyboard button could be dragged to where the keyboard
  appears and then could not be tapped to close it. While the keyboard is
  open the button is now shown (and hit-tested) no lower than 30% of the
  screen height, or just above the entry field being typed into (SDL slides
  the view to keep that field above the keyboard). The saved position is
  untouched and applies again once the keyboard closes.
- A touch outside the entry field being typed into closes the keyboard; a
  touch on that field reopens it (`SDL3GameEngine::updateKeyboardForTouch`).
- Text input starts with `SDL_StartTextInputWithProperties`: text type, no
  capitalization, autocorrect off. SDL maps autocorrect off to
  `UITextAutocorrectionTypeNo` / `UITextSpellCheckingTypeNo`, which removes
  the QuickType predictive bar.

## 2026-09-29: Touch hotkey toolbar, edge scrolling, tap rings, overlay settings (iOS)

The keyboard button moved out of `SDL3GameEngine.cpp` into a dedicated
`SDL3Device/GameClient/SDL3TouchOverlay.cpp` (namespace `TouchOverlay`),
which now holds all on-screen touch controls:

- **Hotkey toolbar**, in a game only: a translucent "Hotkeys" tab at the
  top; tap to open a row of buttons, auto-collapses after 8 s idle. Buttons
  append the game's own meta messages to `TheMessageStream`
  (`MSG_META_SELECT_ALL`, `SELECT_MATCHING_UNITS`, `STOP`, `SCATTER`,
  `VIEW_COMMAND_CENTER`, `VIEW_LAST_RADAR_EVENT`, `OPTIONS`), so they work
  regardless of key bindings. Groups 1-5: tap `SELECT_TEAMn`, long-press
  `CREATE_TEAMn`. The row is laid out with the real font and shrinks until it
  fits the screen width.
- **Sticky Ctrl / Shift**: injected as left Ctrl/Shift key events into
  `SDL3Keyboard`, since the engine derives modifiers from key events. Tap =
  held for the next game gesture (released two frames after it ends, so the
  click message is built while the key still reads as held); long-press =
  locked.
- **Settings page** (Opts): size, opacity, keyboard button on/off,
  double-tap right-click, edge scrolling, tap rings; saved to
  `Documents/touch-overlay.ini` (the old keyboard-button file is migrated).
- **Tap feedback rings** drawn with line segments, white for left clicks and
  orange for right clicks.
- **Edge scrolling** in the gesture translator: a finger resting in the outer
  4% of the screen for 200 ms, and not over an interactive GUI window, enters
  `EDGE_PAN` and scrolls the tactical view each frame with the keyboard
  scroll formula from `LookAtTranslator` (speed factors, frame pacing).
- **Double-tap right-click**, off by default: the first tap has already been
  delivered as a left click (taps are not delayed to wait for a second one),
  which can issue a move order before the right click arrives.

Verified off-device by compiling `SDL3GameEngine.cpp` and
`SDL3TouchOverlay.cpp` against the engine headers on Linux with
`TARGET_OS_IPHONE=1` (and without it), including `-Wall -Wextra`.

## 2026-09-29: Toolbar tab fixed top-right, no auto-close, clear press feedback

From device testing of the hotkey toolbar:

- The Hotkeys/Hide tab is fixed in the top-right corner at one size; the
  button row opens to its left, right-aligned against it.
- No auto-collapse; the open state is saved (`toolbar_open` in
  `touch-overlay.ini`).
- Presses were hard to see: a tap is often shorter than a frame, so the old
  "slightly darker while pressed" state rarely rendered. Pressed buttons are
  now opaque white with black text and a thick border, and every activated
  button flashes (yellow for a tap, green for a long-press) for 250 ms. These
  states ignore the opacity setting. Active Ctrl/Shift use opaque blue
  (one-shot) and orange (locked).

## 2026-09-29: Overlay respects the iOS safe area; Ctrl + group button assigns

- The top-right Hotkeys tab sat on the iPhone's rounded corner. Overlay
  layout now insets by `SDL_GetWindowSafeArea()` (converted from window
  points to display pixels) plus a margin of 2% of the screen height; the
  keyboard button is clamped to the safe area as well.
- Tapping Ctrl then a group button selected the group instead of assigning
  it: the toolbar sends `MSG_META_SELECT_TEAMn` directly, so the injected Ctrl
  key never reached the key-binding lookup. With Ctrl active the group button
  now sends `MSG_META_CREATE_TEAMn` (and releases a one-shot Ctrl), flashing
  green like a long-press assignment.

## 2026-09-29: Touch input dropouts; round group buttons down the right side

**Input stopping for 10-30 s while the game kept running.** SDL on iOS
uses the address of each `UITouch` as the finger id, and UIKit reuses those
addresses. When a finger's up event never arrived, the gesture translator
stayed in `LONGPRESSED` / `PAN` / `EDGE_PAN`, ignored every new touch, and
only recovered once a later touch happened to reuse the stale address and
lift, which gives a random delay. The overlay's press tracking had the same
weakness and could also claim events of a later touch with a reused id. Both
now check each frame that their finger is still in `SDL_GetTouchFingers()`
and reset otherwise (releasing a held button: LMB for a drag, RMB for a
pan), logging `finger lifted without an up event` / `finger no longer on
screen`. A full `SDL3Mouse` event buffer is logged too (rate-limited) instead
of dropping clicks silently.

**Toolbar layout and look.** Ctrl and groups 1-5 moved from the top row into
a column of round buttons down the right side under the Hotkeys tab (8.5% of
the screen height each, circular hit-testing). The top row keeps All, Same,
Stop, Scatter, Home, Alert, Shift, Menu, Opts. Buttons are drawn in an iOS
game-overlay style: rounded pills / circles of dark translucent material
with a thin light rim, iOS system colors for states (blue one-shot, orange
locked, yellow tap flash, green long-press flash, white pressed). Shapes are
filled with 2 px horizontal spans and outlined with arc segments inside one
`beginBatch()` / `endBatch()`, and labels are drawn after the flush. The
keyboard button became a rounded square and steps left of the column while
the toolbar is open.

## 2026-09-29: Cursor (trackpad) mode and D-pad (iOS)

An optional alternative to direct touch, switched from the toolbar's
settings page (`cursor_mode` in `touch-overlay.ini`):

- `SDL3GameEngine.cpp` gained a second gesture translator (`CursorState`):
  one-finger slides move a cursor with speed-based acceleration (gain 1.2
  up to 3.5), a release faster than 150 pt/s keeps it gliding with friction
  0.93 per 1/60 s until a finger touches the screen; tap = left click at the
  cursor; hold 450 ms then slide = left-button drag; two-finger tap = right
  click; two-finger slide scrolls the view (`userScrollBy`, 2.5 offset units
  per display pixel, from `W3DView::scrollBy` mapping through the view plane
  independently of resolution); pinch = wheel at the cursor; the cursor at an
  edge scrolls with the keyboard scroll formula. Same lost-lift recovery via
  `SDL_GetTouchFingers()`. Switching modes releases any held button. In cursor
  mode the on-screen keyboard follows clicks at the cursor.
- iOS shows no system cursor for touch input (`SDL3Mouse` uses SDL system
  cursors), so the overlay draws an arrow, yellow during a hold-drag, over
  everything else.
- **D-pad**: optional round thumb pad on the left edge, in a game. It tracks
  its own finger, so it can be held together with the cursor or any other
  touch. Direction and strength come from the thumb's offset from the center
  (25% dead zone); it scrolls at 1.5x the keyboard scroll amount.
- Polygon fill (even-odd, 2 px spans) was added to draw the arrow and the
  D-pad triangles.

## 2026-09-29: Controller, autosave, FPS limit, render scale, haptics (iOS)

- **Game controller** (`SDL_INIT_GAMEPAD` on iOS): the first connected
  gamepad drives the shared cursor (left stick, squared response, 1.1 screen
  widths/s), scrolls with the right stick, zooms with the triggers, and maps
  buttons to mouse buttons, held Ctrl/Shift (LB/RB, injected key events) and
  meta commands (select matching/all, scatter, groups 1-4 with LB to assign,
  options, command center, radar event, stop). The cursor is shown while the
  controller is in use in either touch mode; a direct touch hides it.
  Assigning a group rumbles the controller.
- **Autosave on leaving the app**: `GameState::saveGame("Autosave.sav")` from
  the lifecycle watcher on `SDL_EVENT_WILL_ENTER_BACKGROUND` (UIKit's
  callback; the app can be suspended before the next frame), campaign and
  skirmish only, at most every 20 s. Any `.sav` name appears in the Load
  menu.
- **FPS limit** (Game / 30 / 60 / 120): re-applied to `TheFramePacer` each
  frame when it differs, since the game sets its own limit at startup, game
  start and from some scripts.
- **Render scale** (100 / 75 / 50%): `SDL3Main.cpp` multiplies the injected
  `-xres/-yres` by `TouchOverlay::renderScale()`, read once at launch; the
  pillarbox blit scales the picture to the full screen and input maps
  through its viewport rect.
- **Haptics**: `UIImpactFeedbackGenerator` via the Objective-C runtime
  (`objc_msgSend`), so no Objective-C++ build setup is needed; light for
  overlay buttons and long-press right clicks, medium for assigning a group
  or locking a key.

## 2026-09-30: Haptics broke the iOS build; packaging now builds first

The haptics code included `<objc/runtime.h>`, whose `typedef bool BOOL`
clashes with DXVK's `windows_base.h` (`typedef INT BOOL`) that the engine is
compiled with, so `SDL3TouchOverlay.cpp` failed to compile on the device
build. The Linux compile check had used stand-in objc headers and missed it.
The three runtime entry points (`objc_getClass`, `sel_registerName`,
`objc_msgSend`) are now declared locally with plain pointer types.

Because `package-ios-zh.sh` packaged whatever engine binary was last built,
the failed build went unnoticed and the phone kept running an old version
(no cursor mode). The script now runs
`cmake --build build/ios-vulkan --target z_generals` first and stops if it
fails (`GX_SKIP_BUILD=1` skips it).

## 2026-09-30: Cursor speed setting

Cursor mode felt too sensitive. A Speed setting (Low / Medium / High /
Extreme, `cursor_speed` in `touch-overlay.ini`) multiplies the cursor gain by
0.45 / 0.7 / 1.0 / 1.5; High is the original tuning and Medium is the new
default. It also scales the controller's left-stick cursor speed.
