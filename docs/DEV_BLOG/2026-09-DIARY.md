# Development Diary - September 2026

---

## 2026-09-28: iOS build needs DXVK's nested header submodules

A fresh iOS build stopped in the DXVK meson configure step with
`ERROR: Problem encountered: Missing Vulkan-Headers`. The README's
iOS quick start ran `git submodule update --init references/fbraz3-dxvk`
without `--recursive`, so the fork's own `include/vulkan` and
`include/spirv` submodules were never checked out. The macOS build can
fall back to the Vulkan SDK headers, but the iOS cross build uses the
iPhoneOS sysroot and has no such fallback.

- `README.md`: the iOS quick start now uses `--recursive`.
- `cmake/dx8.cmake`: the iOS configure fails early with the exact fix
  command when those headers are missing, instead of failing deep in
  the ninja build.

## 2026-09-28: DXVK fails to compile against the iPhoneOS 27 SDK libc++

Building DXVK with Xcode's iPhoneOS 27.0 SDK stops in
`src/dxvk/dxvk_pipemanager.cpp` with libc++ errors from `<tuple>`
("a parameter pack may not be accessed at an out of bounds index",
"no member named '__base_' in 'std::tuple<>'").
`createNullFsPipelineLibrary()` builds its map key with
`std::piecewise_construct` and an empty `std::tuple()`, which that
libc++ no longer accepts. The key is already a default-constructed
local, so `Patches/dxvk-ios.patch` now passes `std::tuple(key)` instead;
the resulting key is identical.

A checkout that already applied the previous patch must reset the fork
first (`git -C references/fbraz3-dxvk checkout -- src`) so the configure
step can apply the updated patch.

## 2026-09-28: iOS packaging fails with duplicate signing certificates

`package-ios-zh.sh` re-signed the app with the name "Apple Development".
With two identical Apple Development certificates in the login keychain
(easy to end up with on a free Personal Team), codesign stops with
"ambiguous" and the app is never installed. When `GX_SIGN_IDENTITY` is
not set, the script now re-signs with the SHA-1 of the certificate Xcode
used for the provisioning shell app, which is also the one the
provisioning profile expects.

## 2026-09-28: iOS install picks a word from the device name

`package-ios-zh.sh --install` took the third-from-last column of
`devicectl list devices` as the device id. Model names with spaces
("iPad Pro (11-inch) ...") shift the columns, so it passed "Pro)" to
`devicectl device install`. The script now matches the identifier
pattern itself and accepts `GX_DEVICE_ID` as an override.

## 2026-09-28: iPad taps land in the wrong place (pillarbox + portrait launch)

On an iPad mini (A17 Pro) the main menu took one tap and then ignored
input. The log showed `Pillarbox: game=800x600, backbuffer=2266x1488`
and no `iOS internal resolution set to` line. Two bugs combined:

- `SDL3Main.cpp` injects `-xres/-yres` from the window pixel size only
  when the window is landscape. An iPad held in portrait at launch reports
  a portrait window before iOS rotates it, so the injection was skipped
  and the engine stayed at 800x600 behind a pillarbox. The app is
  landscape-only, so the long side is now always used as the width.
- `DX8Wrapper::Pillarbox_Setup()` took the backbuffer size from the
  present parameters (pixels) but left the pixel density at 1.0, so
  `Pillarbox_Get_Rect()` returned a pixel rect while touch/mouse input
  arrives in window points. On a 2x display every tap mapped to about
  half its real position. The density now comes from the window even when
  the size comes from the present parameters. Desktop windows are not
  created with high pixel density, so their density stays 1.0.

## 2026-09-28: iPad display collapses into a corner after a device reset

With the resolution fix in place, the main menu worked, but entering the
LAN lobby reset the D3D device and the log showed
`Pillarbox: game=2266x1488, backbuffer=1488x2266`. SDL keeps reporting the
window in portrait on an iPad launched in portrait, even though the
landscape-only app is displayed in landscape, and the reset sizes the
backbuffer from the window. The landscape game was then pillarboxed into a
portrait backbuffer and shown in the bottom-left quarter, with input mapped
to the wrong rect. The SDL3 display size providers in `W3DDisplay.cpp` now
report the long side as width on iOS.

## 2026-09-28: Root cause of the portrait window on iOS: missing SDL_HINT_ORIENTATIONS

An iPhone (A19, launched upright) showed the game squished into the left
half. The log had `iOS internal resolution set to 2622x1206 (window
1206x2622)` and `Created 3 swapchain images with size (1206, 2622)`.

SDL's `UIKit_GetSupportedOrientations()` returns *all* orientations for a
`SDL_WINDOW_RESIZABLE` window when `SDL_HINT_ORIENTATIONS` is unset, so the
view controller allowed portrait and `SetupWindowData()` sized the window
from the portrait screen. This is the common cause of the earlier iPad
issues too (stale portrait window size, portrait backbuffer after a device
reset). `SDL3Main.cpp` now sets the hint to `LandscapeLeft LandscapeRight`
before SDL video init, which makes SDL create the window landscape and keeps
the view controller landscape-only. The earlier landscape normalizations
stay as a defensive fallback.

## 2026-09-28: Log OpenAL device startup in release builds

An iPhone had no sound and the on-device log said nothing about audio:
`OpenALAudioManager::openDevice()` only reported failures through
`DEBUG_LOG`, which release builds compile out, and fell back to "sound off"
silently. It now also writes to stderr when audio is disabled by settings,
when `alcOpenDevice` / `alcCreateContext` / `alcMakeContextCurrent` fail
(with the ALC error code), and which device it opened on success, so the
iOS log can tell a failed device apart from a muted one.

## 2026-09-29: On-screen keyboard can be closed and opened on demand (iOS)

Naming a save game opened the iOS keyboard, which then covered the screen
with no way to close it: `updateTextInputState()` restarted text input every
frame while the entry field had focus, and iPhone keyboards have no hide key.

- `SDL_HINT_RETURN_KEY_HIDES_IME` is set on iOS, so Return closes the
  keyboard (the Return key press still reaches the game).
- When SDL stops text input behind the engine's back (Return, iPad hide
  key), the engine remembers the entry field and keeps the keyboard closed
  until focus moves elsewhere.
- The focused entry field's rect is passed to `SDL_SetTextInputArea()` so SDL
  slides the view up and keeps the field visible above the keyboard.
- New floating keyboard button, drawn translucent on top of the UI
  (`SDL3TouchOverlay_Draw()`, called from `W3DDisplay::draw()`): tap to show
  or hide the keyboard at any time (with no entry field focused, typed keys
  reach the game as key presses); long-press then drag to move it. The
  position is saved to `Documents/touch-keyboard-button.txt`. Touches that
  start on the button never reach the gesture translator.

The button's touch state machine and drawing were exercised off-device
against the SDL 3.4.2 headers (tap toggles, taps elsewhere pass through,
long-press drag moves and persists the position).

## 2026-09-29: Keyboard button stays reachable, tap-outside closes, no predictive bar

Follow-ups to the on-screen keyboard work, from device testing:

- The floating keyboard button could be dragged to where the keyboard
  appears and then could not be tapped to close it. While the keyboard is
  open the button is now shown (and hit-tested) no lower than 30% of the
  screen height, or just above the entry field being typed into (SDL slides
  the view to keep that field above the keyboard). The saved position is
  untouched and applies again once the keyboard closes.
- A touch outside the entry field being typed into closes the keyboard; a
  touch on that field reopens it (`SDL3GameEngine::updateKeyboardForTouch`).
- Text input starts with `SDL_StartTextInputWithProperties`: text type, no
  capitalization, autocorrect off. SDL maps autocorrect off to
  `UITextAutocorrectionTypeNo` / `UITextSpellCheckingTypeNo`, which removes
  the QuickType predictive bar.
